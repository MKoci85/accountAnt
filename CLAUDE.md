# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@AGENTS.md

## What this is

A personal, single-user expense tracker for use in Uruguay, built to surface "gastos hormiga" (small, impulsive purchases) and support a savings-focused budget — not a general-purpose or multi-tenant product. 100% local, no login/auth. Everything runs in one Next.js process (`npm run dev` / build+start) — no separate backend.

## Commands

```bash
npm run dev            # start dev server (Turbopack)
npm run dev:https       # dev server over HTTPS (needed for camera/QR scan from a phone on the LAN — see README)
npm run build           # production build
npm run lint             # ESLint (flat config, eslint-config-next)
npm test                 # Vitest, una sola pasada
npm run test:watch       # Vitest en watch
npx tsc --noEmit         # typecheck (no dedicated typecheck script)

npm run db:generate      # generate a Drizzle migration from schema changes
npm run db:migrate       # apply migrations to ./data/control-gastos.db
npm run db:studio        # Drizzle Studio GUI
```

Verification for a change is: `npm test`, `npm run lint`, `npx tsc --noEmit`, and manually exercising the flow via `npm run dev`.

**Tests are Vitest, node environment, and cover pure functions in `src/lib/` only** (`src/lib/*.test.ts`, config in `vitest.config.mts`, `@/` aliased to `src/`). There is deliberately no component, server-action or DB test: those need a running SQLite file or a DOM, and the maintenance cost was judged not worth it for a single-user app. What *is* covered is the arithmetic and the parsers that fail silently — `montoDeLinea`/`normalizarLineasDeServicio`/`lineasDesdeTicket`, `parsearTamano`/`superaReferencia`, `parsearMonto` (both of them — `lib/formato.ts` reads what the user types, `lib/estado-cuenta.ts` reads the PDF's own format), `parsearQR`/`parsearNombreItem`, `podarHistorial`/`separarReporteAdjunto`/`limpiarRespuestaChat`, `clasificarLinea`, `agruparEnFilas`/`redactarDatosPersonales`. When you change one of those, the test is the spec — update it deliberately, don't delete the case.

`cfe.test.ts` has `vi.mock("@/db", ...)` for hygiene, not to avoid a crash: `lib/cfe.ts` imports `lib/config-server.ts`, which imports `@/db`, which opens `./data/control-gastos.db` **at import time**. It does not throw on a fresh clone — `data/.gitkeep` is committed, so the directory exists and SQLite just *creates* an empty file — but a unit test of a pure parser has no business opening a DB handle or leaving a stray `.db` + `-shm` + `-wal` behind. Nothing about the CFE parsing itself is mocked.

## Architecture

- **Next.js 16 App Router + TypeScript**, React 19. Pages live under `src/app/`: `/` (dashboard), `/gastos`, `/gastos/nuevo`, `/gastos/[id]`, `/gastos/[id]/editar`, `/gastos-fijos`, `/catalogos`, `/reportes`, `/reportes/asistente`, `/reportes/asistente/[id]`, `/estado-cuenta`, `/ajustes`.
- **Data layer**: Drizzle ORM over SQLite (`better-sqlite3`). `src/db/index.ts` opens `./data/control-gastos.db` (WAL mode, FK enforcement on) and exports `db`. Schema lives in `src/db/schema/` split into `catalogos.ts` (reference/lookup tables), `gastos.ts` (transactional tables), `gastos-fijos.ts`, `configuracion.ts` and `chat-ia.ts`, re-exported via `schema/index.ts`. `drizzle.config.ts` points `drizzle-kit` at the same schema and DB file; migrations are checked into `./drizzle/`.
- **UI components**: shadcn/ui (`style: base-nova`, base color neutral) copied into `src/components/ui/` — edit these directly, they are not an npm dependency. Path aliases: `@/components`, `@/components/ui`, `@/lib`, `@/hooks` (see `components.json`). Icons via `lucide-react`.
- **Server actions**: `src/app/actions/gastos.ts` (`guardarGasto`, `crearGasto`, `editarGasto`, `borrarGasto`, `combinarGastos`, `obtenerGasto`, `listarGastos`, `obtenerResumenDashboard`, `obtenerReferenciasDePrecio`), `src/app/actions/catalogos.ts` (CRUD for categorías, ítems de catálogo, emisores, plus `guardarProveedorEmisor` and CRUD for proveedores de CFE), `src/app/actions/gastos-fijos.ts` (`listarGastosFijos`, `crearGastoFijo`, `editarGastoFijo`, `cambiarActivoGastoFijo`, `borrarGastoFijo`, `pagarGastoFijo` — the recurring-expense flow described below), `src/app/actions/cfe.ts` (`consultarCFE` — the QR-scan orchestration described below — and `interpretarTicket`, the AI reading of a QR-less receipt photo), `src/app/actions/estado-cuenta.ts` (`analizarEstadoCuenta`, `analizarEstadoCuentaConIA`, `importarMovimientos` — the statement-import flow described below), `src/app/actions/ia.ts` (`probarConexionIA`, `interpretarEstadoCuentaConIA`, `interpretarTicketConIA`), `src/app/actions/chat-ia.ts` (`listarConversaciones`, `obtenerConversacion`, `crearConversacion`, `enviarMensaje`, `renombrarConversacion`, `borrarConversacion`, plus the attached-report flow — `destinosParaReporte`, `prepararReporteParaChat`, `reutilizarAdjunto`, `descartarAdjuntoPendiente` — the chat assistant described below), `src/app/actions/configuracion.ts` (settings for `/ajustes`: IA provider/model/API-key/rate-limiter state, plus the advanced thresholds — `margenSobreprecioPeso`, `ventanaMesesReferencia`, BCU/DGI/IA endpoint URLs and timeouts). All pages read/write the DB through these; there is no hardcoded/mock data left.
- **Reportes** (`src/app/actions/reportes.ts`): `obtenerReporte(filtros)` walks the period's expense lines once and derives every block (resumen, categorías, ítems con sobreprecio, comercios, evolución mensual, matriz hormiga×sobreprecio) from that single pass. Price references (`obtenerReferenciasPrecio`) are computed over the *whole* DB, not the filtered period — the cheapest known price for a product doesn't stop being valid because the filter excludes it. `exportarReporteJSON` wraps the same data with a `contexto` + `glosario` block: the JSON is meant to be read by an AI that knows nothing about this app, so it must be self-explanatory — it feeds both "Copiar JSON para IA" (to paste into a third-party chat) and "Analizar con IA" (which hands it to the built-in assistant without the JSON ever reaching the browser; see the chat-assistant notes). Every amount in the export is rounded to 2 decimals (`redondearMonto`) — totals accumulate through floating-point multiplication (`cantidad × precio`, and a per-kilo price is already a division), so without it the JSON shows `225.01694000000001` instead of `225.02`. Charts use `recharts` (`src/components/reportes-graficos.tsx`, client-only) with the `--chart-N` tokens from `globals.css`.
  - **Drill-down to `/gastos` travels as exact dates, not as a named range.** The rows of "Qué estás pagando de más" and "Dónde comprás" link to `/gastos?desde=…&hasta=…` (plus `emisor` or `q`), and `GastosView` gained a `personalizado` entry in `rangosFecha` to receive them: its other ranges are windows relative to today (7d/30d/este mes), so without it the link would have to land on the closest one — i.e. lie about which period is on screen. `GastosView` reads the query string **once, at mount** (lazy `useState` initializers) and never writes back: syncing the other way would mean a history entry per keystroke of the search box.
- **Gasto form** (`src/components/nuevo-gasto-form.tsx`, `src/lib/lineas-gasto.ts`, `src/components/linea-gasto-fila.tsx`, `src/components/combobox-busqueda.tsx`): the page where a twenty-item supermarket run gets typed in, so the cost of every extra gesture is multiplied by twenty.
  - **`LineaGasto.precio` is `number | ""`, and `""` is not 0.** A new line starts with an empty price input; starting at 0 meant deleting the zero before typing, once per line. Everything that computes with it goes through `montoDeLinea` (`lib/lineas-gasto.ts`) — total, `sobreprecioDeLinea`, `motivoNoGuardable`, and the payload sent to `crearGasto`, which is the one place the empty collapses back to a number.
  - **`motivoNoGuardable()` returns the reason, not a boolean.** `puedeGuardar` is derived from it (`=== null`), so the guard is unchanged, but the disabled button now says *which* of the five conditions is missing — with twenty lines loaded, spotting the one with no price by eye is exactly what can't be asked of the user.
  - **`ComboboxBusqueda` is the one dropdown for the form's three searches** (comercio, ítem nuevo, and the per-line `BuscadorItemLinea` that resolves a ticket line). The logic used to be triplicated as `div` + `button` + `onMouseDown` with no keyboard at all. The component owns the interaction only — arrows/Enter/Escape, the ARIA `listbox`/`option` pair, and the highlight reset on a new result list (adjusted **during render**, not in an effect, so the stale index is never painted). The **search stays in each caller**: the three debounce against their own action and resolve differently — the comercio one stops searching once one is picked, which is what `suspendido` expresses. The final row ("+ Crear ítem nuevo") is navigable like any option, because it's what gets chosen when the search comes back empty.
  - **Leaving with unsaved lines asks first** (`huellaFormulario` + `beforeunload`). Dirtiness is a comparison against the snapshot taken at mount, not a `tocado` flag set by each mutation: a dozen functions write `lineas`, and one of them forgetting to mark would make the warning silently useless. It also gets the revisión flow right for free — there the lines arrive pre-loaded, so "Salir"/"Saltear" stay silent until something is actually touched.
  - **The scanned total is cross-checked, never enforced.** `consultarCFE` already returns a DGI-validated `total`; the form shows the gap against the sum of its lines when it exceeds $1. It does **not** block saving — deleting a line on purpose is a legitimate reason for the numbers not to match. It is skipped entirely when `avisoMoneda` is set: there the total was left unconverted from USD, so the difference would be invented (see the QR/CFE notes below).
  - The two capture panels fold behind a button on mobile, in pure CSS (`hidden md:flex`) rather than a media-query hook — no duplicated component instances, and no server-rendered state for the client to correct. Desktop's side column is untouched.
  - **`esPesoDesconocido` (`gastoItems`) exists because a scale ticket sometimes doesn't print the weight at all**, and forcing a number there would mean inventing one. Toggling it on a kg/L line (`LineaGastoFila`, only offered when `unidad !== "un"`) blanks and disables the cantidad input, forces `precio` to mean the line's **total paid** instead of a per-kilo rate, and clears any sobreprecio/precio-base state on that line — the expense is still logged, it's just excluded end to end from price comparison: `conSobreprecioDetectado` (`actions/gastos.ts`) short-circuits it to `esSobreprecio: false` before the catalog lookup, and both `obtenerPreciosMinimos` (`actions/gastos.ts`) and `obtenerReferenciasPrecio` (`actions/reportes.ts`) skip the row entirely so an unknown weight can never become another purchase's reference price. Switching the unit back to `"un"` clears the flag, since "unknown weight" isn't a concept that applies to a piece-priced line.
- **Líneas sin catálogo y líneas de servicio** (`LineaGasto.sinCatalogo`, `categorias.esServicio`, `esLineaDeServicio` / `normalizarLineasDeServicio` / `lineaLibreNueva` in `src/lib/lineas-gasto.ts`): a dentist visit, a month of UTE and a subscription are all the same line shape — no catalog item, free-text `descripcion`, `cantidad: 1`, `unidad: "un"`, one amount. Asking them "se vende por: unidad / kilo / litro" is a question with one possible answer, so the form stops asking.
  - **The flag lives on the categoría, not on a hardcoded list of names.** The user creates categories, so a list in code would make the next one ask for kilos again. `esServicio` is editable from `/catalogos` (`NuevaCategoriaDialog`, plus a "Servicio" badge in the list) — which is why `crearCategoria` switched from positional args to an object: a fourth optional positional ages badly. Migration `0019_categorias_servicio.sql` seeds Servicios/Vivienda (new, service) and Farmacia (new, *not* a service — a medicine is catalogable, and its presentation is `tamano`, exactly like "Leche 1L"), and marks Salud/Suscripciones. It also **moves the pharmacy keywords out of Salud**: `sugerirCategoriaPorTexto` (`actions/catalogos.ts`) walks categories with no `ORDER BY` and returns the first match, so leaving "ibuprofeno" in both would make the winner depend on SQLite's row order.
  - **Nothing in the data model changes**, and no exception is written anywhere for price comparison: a service line has `itemCatalogoId: null`, and `conSobreprecioDetectado` (`actions/gastos.ts`) already short-circuits those to `esSobreprecio: false`.
  - **"No tiene ítem de catálogo" and "es un servicio" are two independent axes, and collapsing them into one was a real bug.** `LineaGasto.sinCatalogo` carries the first (the name was typed by hand and the line never expects to be linked to anything); `categorias.esServicio` carries the second (one amount instead of cantidad + unidad). Crossing them yields the four cases with no special-casing anywhere: a catalog item; a ticket line still to be catalogued (buscador + "sin catalogar" notice); UTE (free text, single amount); and **a one-off purchase not worth cataloguing — a uniforme deportivo under Otros — which is free text and keeps cantidad**. `motivoNoGuardable` (`nuevo-gasto-form.tsx`) and `LineaGastoFila` both read the flag, never the id. What *is* validated is the name: an empty one would be stored as `descripcion: ""` and come back as "Sin detalle".
  - **A free line gets no "se vende por" selector, even outside a service categoría.** `unidad` exists so that price comparison is meaningful (a per-kilo price is never compared against a per-piece one), and a line with no `itemCatalogoId` is structurally excluded from that comparison everywhere it is computed — so the control would be a knob whose only purpose doesn't apply, and it was cramping the narrow first grid column for no gain. `eligeUnidad` (`LineaGastoFila`) keeps showing it when a *stored* free line carries a `unidad` other than `"un"`, so a row saved that way before this (the `-1` bug below could mint one from a weighed ticket line) stays repairable instead of stranded.
  - **The flag exists because the `item.id === -1` sentinel it replaced did not work.** `contadorItemProvisorio` starts at `-1` and post-decrements, so the *first* uncatalogued line of a scanned ticket was born with exactly `-1` — the value the guard exempted — and could be saved without ever being linked, while the second one (`-2`) was correctly blocked: two identical-looking lines behaving differently depending on the order things happened in one page load. With the flag, the id of an uncatalogued line means nothing at all; it is only ever compared with `> 0`. Don't hang semantics off a magic number there again.
  - **The total is always `cantidad × precio`, so a hidden cantidad can never be ≠ 1.** `normalizarLineasDeServicio` runs on every set of lines entering the form (loaded gasto, scanned ticket, categoría change) and collapses `3 × $500` into `1 × $1.500` — the money is preserved, and the conversion is listed line by line in a notice above the total because it only reaches the DB when the user saves. Without it, a gasto from a categoría marked as a service *after* it was loaded would show "Importe $500" and total $1.500.
- **Gastos fijos** (`/gastos-fijos`, `src/app/actions/gastos-fijos.ts`, `src/components/gastos-fijos-view.tsx`, `gasto-fijo-dialog.tsx`, `pagar-gasto-fijo-dialog.tsx`): a gasto fijo is not a new concept — it's a service line saved as a template, which is why it builds on the section above and its generated line renders correctly in the edit form for free.
  - **`gastosFijos.categoriaId` *is* the "tipo"** (Servicios, Suscripciones, Vivienda, Salud), not a second taxonomy: `/reportes` and the chat assistant already understand categorías.
  - **`gastos.gastoFijoId` is what makes the screen worth having.** It answers the only question asked of it — *¿ya lo pagué este mes?* — and with it come the badge ("Pagado el 3/9" vs. "Pendiente"), the amount pre-filled from the last payment (when it *doesn't* match, that mismatch is the useful signal), the duplicate warning, and the per-template history with no emisor+monto+mes heuristics. The duplicate warning is needed because `gastos`' unique index is partial (`WHERE serie IS NOT NULL`), so two taps would silently write two identical gastos.
  - **The last payment's amount is summed from `gastoItems`, not read from `gastos.montoTotal`** — `editarGasto` doesn't touch `montoTotal`, so editing the gasto would leave the card quoting a stale number.
  - **`onDelete: "set null"`, and the generated `ALTER TABLE` needed fixing by hand**: `drizzle-kit` emitted the added column as a bare `REFERENCES gastos_fijos(id)`, dropping the `ON DELETE set null` the schema declares — which would have made deleting a paid template fail on the FK. Check the generated SQL when adding a FK column.
  - **`activo` instead of deleting**: Netflix gets cancelled and the history still explains itself. Archived templates stay visible in their own section with "Reactivar" — archiving must not be a one-way trap. Real deletion stays available, and the confirm dialog says how many already-registered gastos will lose the link.
  - **`pagarGastoFijo` calls `guardarGasto`, not `crearGasto`**: the latter ends in `redirect("/gastos")`, and `redirect` throws — impossible to call from a modal that doesn't want to navigate. `guardarGasto` holds the transaction, the sobreprecio detection and the `UNIQUE` `catch` (which has to stay inside it, or the friendly message is lost); `crearGasto` is a three-line wrapper that revalidates and redirects.
  - The generated gasto is **a normal gasto**, which is what lets `/estado-cuenta` match it against the card's line with the logic that already exists (date ±1 day and amount).
  - **The importe field is a text `Input` + `parsearMonto`, not `type="number"`** — the Spanish-layout phone keyboard types a comma, and `type="number"` swallows it, so "1,240" would arrive as an empty value. Same reason `pagar-gasto-fijo-dialog.tsx` shows the gap against the last payment as prose ("El último fue $637 — $603 más") instead of validating it away.
  - **`borrarCategoria`/`borrarEmisor` gained a `SELECT` against `gastosFijos`, for the message, not for integrity** — with FK enforcement on, SQLite already rejects the delete; what it doesn't do is say *which* template is in the way.
  - The nav entry is labelled **"Fijos"**, not "Gastos fijos": adding it took the mobile bottom bar to six 11px labels (`nav.tsx`, which drops `/ajustes` there), and the full name is longer than every other one.
- **QR/CFE flow**: `src/components/escaner-comprobante.tsx` decodes a receipt QR client-side (camera or uploaded photo, via `jsqr`) and hands the raw string to `consultarCFE` (`src/app/actions/cfe.ts`), which parses it (`parsearQR` in `src/lib/cfe.ts`), validates it against DGI, resolves/creates the `emisores` row by RUC, and — if a proveedor de CFE is mapped — fetches line-item detail from that provider (URL resolved through the `proveedoresCfe` FK).
  - **`proveedoresCfe.formato` picks the request/parse implementation, and it's data, not a hardcoded assumption.** `consultarProcesador` (`src/lib/cfe.ts`) switches on it: `"scanntech"` → `consultarScanntech` (POST, HTML table rows), `"taface"` → `consultarTaface` (GET, items as embedded JSON — see below), anything else (`"sicfe"`, `"otro"`) throws a clear "not implemented" error instead of silently parsing nothing. `FORMATOS_PROVEEDOR_CFE` (`src/lib/procesadores.ts`) is the single source of truth for the enum — reused by the Drizzle column (`text({enum})`, so a future *supported* format is one array entry, no migration) and by the `<select>` in `ProveedorCfeDialog`/the "map a provider" flow in `EscanerComprobante`, whose option values double as the stored `formato`.
  - **TA-Face doesn't need its AJAX search form at all.** The `consulta.aspx` form is a GeneXus SPA (`GXState`, session tokens) that would be real work to reproduce — but its result page (`wpcomprobanteview.aspx`, the URL saved as `urlConsulta`) accepts the same data directly via GET, comma-joined like Scanntech's DGI-style URLs, just in a different order and with no fecha: confirmed against a real e-Ticket from Bantey S.A. (`ruc,tipoCfe,numero,serie,monto,hash`). Unlike Scanntech, items don't need table-row parsing: they arrive as JSON in a hidden input (`Grid1ContainerDataV`), one array per item — `[nro, iva%, articulo, "", cantidad, um, precioUnitario, descuento, monto]`. "Not found" doesn't come back as a distinct error page like Scanntech — TA-Face always responds 200 with the same structure, and an empty grid array is the only signal.
  - **Each line's `monto`/`precio` in TA-Face's grid is net of IVA, not what the customer paid for that line** — confirmed against the same Bantey receipt, where the printed line amount (177,87) is exactly what the receipt's own totals section lists as "Sub Total Gravado a IVA 22%", separate from the 39,13 of IVA that gets added to reach the real total (217,00). `conIvaDeLinea` grosses up each line using its own `%IVA` column (can differ within one ticket — 22%/10%/0%), rounding to cents to absorb the float remainder (`177.87 * 1.22 = 217.0014`, not `217.00`). Scanntech's parser doesn't have this — its HTML rows don't expose a per-line IVA%, and no real Scanntech receipt has shown the same net/gross gap, so it's left alone rather than guessed at.
  - **A CFE can be in a currency other than pesos, and the app didn't used to know that.** `DetalleComprobante.moneda` is null when the provider doesn't expose it (Scanntech's HTML, in every ticket tested so far) — TA-Face does, in `span_vTOTTPOMONEDA`. `consultarCFE` converts to pesos when it's `"USD"`, using the BCU quote for the QR's own date (`obtenerCotizacionCacheada`, shared with the statement-import flow below — moved out of `estado-cuenta.ts` so both call sites hit the same `cotizaciones` cache instead of duplicating the lookup). Same principle as statement import: **never assume a rate** — an unsupported currency or a BCU miss leaves the detail unconverted and returns `avisoMoneda` (deliberately separate from `errorProveedor`, which drives the "map a provider" UI and doesn't apply here — the provider *did* answer) so the UI can show the original-currency amount and let the user complete it by hand instead of silently saving USD as if it were UYU.
  - **uCFE (Uruware) is the third processor, and it's shaped nothing like the other two.** `consultarUcfe` (`src/lib/cfe.ts`) first GETs `ConsultarCFE.aspx?rut=...` to pull a fresh ASP.NET WebForms triad (`__VIEWSTATE`, `__VIEWSTATEGENERATOR`, `__EVENTVALIDATION`) and session cookie out of the HTML, then POSTs the QR fields back at the same URL with that triad — the cookie has to travel on both requests, or the postback is rejected. "Not found" and "bad security code" are distinct HTML strings on the result page (unlike Scanntech's error page or TA-Face's always-200-empty-grid), so they're matched and thrown as separate errors. Item detail isn't in that HTML at all: it comes from a **separate PDF** (`DescargarPDF.aspx`, same directory as `urlConsulta`, same cookie), extracted positionally with `unpdf` — reusing the exact tool `estado-cuenta.ts` uses for statement PDFs — then parsed line-by-line by `parsearItemsPdfUcfe` against the printed column header (`Descripción Uni * P.Unitario Desc Rec Cantidad Importe`); a name that wraps across lines is accumulated until a row actually matches the `UN|KG|LT|...` line pattern. If the PDF fetch fails or isn't actually a PDF, the function still returns the emisor/total from the HTML with an empty item list rather than throwing — partial detail beats none.
- **Ticket sin QR** (`src/components/lector-ticket-ia.tsx`, `interpretarTicket` in `src/app/actions/cfe.ts`, `interpretarTicketConIA` in `src/app/actions/ia.ts`): a photo of a receipt or handwritten "nota de pedido" that has no QR, read with AI from `/gastos/nuevo`. It is the counterpart of the QR scan, not of `/estado-cuenta`: **the photo is ONE purchase with N items**, so it fills the gasto form's lines (via the same `lineasDesdeTicket`) and nothing is written until the user saves. `/estado-cuenta` stays for card statements, where each line genuinely *is* a separate purchase — reading a detailed ticket there produced one gasto per product, which is what this exists to avoid. That page now takes **PDF only**: the image path was removed from `analizarEstadoCuentaConIA` (its argument is `{ buffer }`, no longer a `FuenteIA`) so there is exactly one place where a photo is read.
  - **The camera is live `getUserMedia`, not `capture="environment"` on a file input** — same as `EscanerComprobante`. `capture` only does something on a phone; on desktop it left two buttons that both opened the file picker. The stream is requested at `width/height: {ideal: 1920/1080}` because the default is around 640×480, where a receipt's prices are unreadable for the model, and the preview is `object-contain`: the captured frame is the whole video, so what is framed has to be what gets sent. The live-preview UI itself (`src/components/vista-camara.tsx`) is shared with `EscanerComprobante` — both used to carry their own inline `<video>` + close button; `VistaCamara` is a fixed full-screen overlay instead (locks `body` scroll, closes on Escape) so the frame gets real screen space instead of a `max-h-[55vh]` box, with an optional bottom `accion` button for the flows (this one) that need an explicit shutter, and none for the ones (QR scanning) that capture on their own as soon as a code decodes.
  - `PROMPT_EXTRACCION_TICKET` asks for an **object** (`{comercio, fecha, items}`), not the flat array of `PROMPT_EXTRACCION` — that shape is what keeps the items attached to one purchase. `extraerJSON` therefore takes the delimiters to slice on: cutting an object at the first `[` would return `items` without the header.
  - Items are resolved against the catalog with the very same `resolverItemContraCatalogo` the QR flow uses, so a photographed item matches `itemsCatalogo`, gets its category suggested by text, and takes part in sobreprecio detection exactly like a scanned one. `cantidad` from the ticket goes to `unidadesTicket`, and `precio` is the line **total** (`camposDesdeTicket` divides it): "2 Leche $110" becomes 2 un × $55.
  - **A weighed line (`peso`/`precioPorKilo` in `PROMPT_EXTRACCION_TICKET`) is read the same way the QR flow reads Scanntech/TA-Face/uCFE's own peso columns**, not guessed from the name. The model is asked to convert everything to kilos in the JSON itself ("320 g" → `0.32`, "1/2 kg" → `0.5`) because that normalization is easier for it to get right than for a regex to reverse-engineer from free-text units after the fact; `pesoOpcional`/`importeOpcional` (`actions/ia.ts`) still validate the result (reject non-positive, parse a bare fraction) rather than trusting it blindly. When `precioPorKiloTicket` comes back, `camposDesdeTicket` (`lib/lineas-gasto.ts`) takes it as the line's `unidad: "kg"` price straight away — checked *before* the `tamanoTicket` fallback, since a weighed line has no fixed tamaño to parse.
  - **Duplicate items on one ticket are merged before they become form lines** (`agruparRepetidas`, `lib/lineas-gasto.ts`), not left as N rows the user has to notice and combine by hand — a receipt reading two separate "Coca Cola 1.5L" lines (same register scan twice) is one line with `cantidad` summed. The grouping key is item + categoría + unidad + precio (rounded to cents) — same item at a different price is *not* the same purchase decision and stays split — plus, for weighed lines, whether `esPesoDesconocido` is set, so a line with a known weight never merges into one without.
  - **The comercio is searched, never created**: the name comes from a photo and may be misread, so an exact match is selected and anything else is just left typed in the search box for the user to resolve.
- **AI providers** (`src/lib/proveedores-ia.ts`, `src/lib/config-server.ts`, `src/lib/ia-cliente.ts`): optional, opt-in, used by `/estado-cuenta`, by the ticket reader at `/gastos/nuevo` and by the chat assistant at `/reportes/asistente`. Six providers — Anthropic, Gemini, OpenAI, Groq, OpenRouter, OpenCode Zen.
  - **Only Gemini, Groq, OpenRouter and OpenCode Zen are actually in use** (all four have a free tier; all four have a key configured). **Anthropic and OpenAI are ruled out for now** — they are pay-as-you-go and the user does not intend to pay for them. So: don't propose configuring, testing or verifying anything against those two, and don't leave work depending on a manual check that needs one of their keys. Their rows stay in `PROVEEDORES` because the code is provider-agnostic and a key could appear later. Concretely, this makes the chat's Anthropic prompt caching **dead code today**: `cachear` is gated on `soportaCache`, which only Anthropic declares. The open models the user might want (Llama, DeepSeek, Qwen, Kimi, GLM) are already reachable **as models inside Groq and OpenRouter** — that is what the editable `modelo` field is for; no new provider row is needed.
  - **`PROVEEDORES` is the single source of truth, and it is data, not branches.** Each row carries `formato` (`"anthropic" | "gemini" | "openai-compatible"`) plus `baseUrl`, `headersExtra`, `campoMaxTokens`, `avisoPrivacidad`. `llamar()` (in `src/lib/ia-cliente.ts`) switches on `formato`, so OpenAI, Groq and OpenRouter share one branch: adding another OpenAI-compatible provider is a new row, not new code. `campoMaxTokens` exists because OpenAI rejects `max_tokens` on newer models and wants `max_completion_tokens`, while Groq/OpenRouter still take the old one.
  - **Storage is in the `configuracion` key/value table — no schema migration.** `ia_api_key_<proveedor>` (one per provider, all kept at once, so switching providers never means re-pasting a key), `ia_modelo_<proveedor>` (absent = the code default), `ia_proveedor` (the active one), `ia_limitador_activo`, `ia_url_<proveedor>` (endpoint override), `ia_tpm_<proveedor>_<modelo>` and `ia_rpd_<proveedor>` (quota overrides), `ia_modelos_<proveedor>` (the suggested-model catalog), `ia_timeout_chat_ms` (the chat's own timeout, 45s — separate from `ia_timeout_ms`, which is 120s and sized for a whole PDF). Note `ia_ultimo_uso_*` is **gone**: it belonged to the pre-`usoIA` limiter and migration `0013_borrar_ultimo_uso_ia.sql` deletes those rows.
  - **The raw API key must never be exported from a `"use server"` file** — everything such a module exports is callable from the browser. Keys are read in `config-server.ts` (deliberately not `"use server"`); actions only return a masked version. Preserve this invariant.
  - **Legacy migration**: the older single global `ia_api_key` is copied to `ia_api_key_<proveedorActivo>` on first read **and deleted in the same transaction**. The delete is not optional: that row is anchored to whatever `ia_proveedor` currently says, so a surviving legacy row gets re-attributed when the active provider changes — which would send one provider's key to another provider's API.
  - **Model IDs go stale**, which is why the model is editable per provider from `/ajustes` and the code default is only a starting point (Groq's `qwen/qwen3.6-27b` is a preview model; OpenRouter's `:free` catalog rotates). Verify against the live API before changing a default, and prefer vision-capable models — the "photo of a receipt" flow needs image input.
  - **Model suggestions** (`catalogo` in `PROVEEDORES`, `actualizarModelosProveedor` in `actions/configuracion.ts`): the two providers whose free catalog rotates — OpenRouter and OpenCode Zen — declare a `catalogo: { url, urlListado, esGratuito }`, and `/ajustes` shows an "Actualizar modelos" button that refreshes a `<datalist>` from their public, unauthenticated `/models` endpoint. The other four don't declare it and get no button: their catalogs are stable. The field stays a free-text `<input list=...>`, never a `<select>` — a stale catalog must never become a cage. `esGratuito` is a per-provider function because the two express "free" differently: OpenRouter has `pricing.prompt === "0"` **plus** a check that text is the *only* output modality (its free tier includes audio-generation models that declare `["text","audio"]` and would otherwise be suggested for chat); Zen publishes no pricing at all and encodes it in the id's `-free` suffix. Stored as one `ia_modelos_<proveedor>` key in `configuracion` (JSON, no migration), **rewritten whole** on each update — that is what makes a retired model stop being suggested, with no delete logic. A corrupt value degrades to "never updated" rather than breaking `/ajustes`, and a valid response with zero free models is not saved (it would wipe good suggestions during a provider hiccup). It spends no AI quota: a public GET, no key, no inference to record in `usoIA`.
  - **Model output is not assumed to be clean JSON.** `extraerJSON` strips `<think>`/`<thinking>` blocks *before* looking for the array (reasoning models emit them, and that prose can contain brackets), then tries the fenced block, then the outermost `[`…`]`. Don't collapse it back into a `JSON.parse` of the raw text.
  - **A reasoning model's thinking tokens come out of the *response* budget, and a truncated answer is never presented as a finished one.** Measured against Gemini (`gemini-3.6-flash`) with the chat's old 1024-token ceiling: one answer spent `thoughtsTokenCount: 670` thinking and 350 writing, came back `finishReason: MAX_TOKENS` with prose cut mid-word — and was stored as if complete, so the user had to ask the model whether it had been cut off. Two knobs fix the budget, both data in `PROVEEDORES`: `maxTokensChat` raises the ceiling **per provider** (Gemini: 4096; it has 250k TPM so it costs nothing, while raising the global constant would eat Groq's context — `limiteContexto` subtracts the ceiling from the TPM), and `nivelRazonamiento` sends `generationConfig.thinkingConfig.thinkingLevel`. That field only exists on the 3.x models, so a 400 whose body mentions "thinking" is retried once without it — the model is user-editable in `/ajustes` and must not be able to break the call. Separately, `llamar()` reports `truncado` in all three formats (`finishReason: MAX_TOKENS` / `stop_reason: "max_tokens"` / `finish_reason: "length"`) and `enviarMensaje` appends `MARCA_RESPUESTA_CORTADA` to what it stores: the partial answer is kept (it was already paid for) but the cut is visible to the user and to the model on the next turn.
  - **Rate limiter** (`src/lib/limitador-ia.ts`): `estadoCuota(proveedor, modelo, tokensPedidos)` / `registrarUso(...)`, backed by the `usoIA` table (one row per request, not a timestamp that gets overwritten — counting requests in a window needs rows). There is no single limit to model: three independent axes are checked and the most restrictive wins — **RPM** and **RPD** (per account/provider) and **TPM** (per provider+**model**, because that is how Groq defines it). A provider that declares none of them is never throttled: the absence of data *is* the data, which is what keeps pay-as-you-go providers (Anthropic, OpenAI) from being blocked for no reason. Defaults live in `PROVEEDORES` and `/ajustes` overrides them per provider (`ia_rpd_<proveedor>`) and per provider+model (`ia_tpm_<proveedor>_<modelo>`). RPD is counted by **local calendar day** — deliberately an approximation, since providers use UTC or rolling windows; it's a defensive warning, not a mirror of their counter. Usage is recorded *before* the call (quotas are rolling windows counted from when the request goes out) and stays recorded even if the call fails, since those tokens were spent anyway. Turning the limiter off (`ia_limitador_activo`) removes the brake but **still counts usage** — switching off the brake shouldn't switch off "how many queries do I have left today". `probarConexionIA` is exempt from the brake but does record (`origen: "test"`): a connection test spends the same daily quota as a real message. `origen` (`"chat" | "estado-cuenta" | "ticket" | "test"`) is diagnostic only — never filter the quota count by it — and its type is derived from the schema (`typeof usoIA.$inferInsert`) so adding a flow doesn't mean editing the union in two places. It's a Drizzle `text({enum})`, i.e. TypeScript-only: adding a value needs no migration.
- **Statement import** (`/estado-cuenta`, `src/app/actions/estado-cuenta.ts`, `src/lib/estado-cuenta.ts`, `src/lib/pdf.ts`, `src/lib/clasificacion-comercios.ts`, `src/lib/bcu.ts`): a card statement PDF is parsed positionally with `unpdf` (never OCR) — `src/lib/pdf.ts` reconstructs lines from raw glyph positions, and `estado-cuenta.ts` splits UYU vs. USD by which x-range the amount falls in (detected from the "USD" column header when present, with a hardcoded fallback range documented inline). Each movement is classified into a `RubroDirecto` (`combustible` | `telepeaje` | `suscripcion`, `clasificacion-comercios.ts`), matched against existing `gastos` (by date ±1 day and amount, counting occurrences to survive same-day repeats), or offered as a missing expense. USD amounts are converted with `src/lib/bcu.ts` (BCU SOAP `wsbcucotizaciones` service, code 2222): a weekend/holiday query returns zeroed amounts, so it queries a date range and walks back to the last available quote, then caches the result in the `cotizaciones` table via `obtenerCotizacionCacheada` (also `bcu.ts`) so the same date isn't re-queried per line — shared with the QR/CFE flow above, which hits the same cache for USD comprobantes. `emisorAlias` maps a POS statement name (e.g. "SUPERMERCADOS ESTEFAN") to an existing `emisores` row — mapped once by hand, resolved automatically after. `combinarGastos` (`actions/gastos.ts`) merges duplicate gasto rows that both a QR scan and a statement import produced.
  - **Fuel doesn't collapse to one emisor per brand.** `MARCAS_COMBUSTIBLE` (`clasificacion-comercios.ts`) only *recognizes* a line as fuel (it includes discontinued brands whose text still shows up on the POS — ESSO→AXION, PETROBRAS→DISA — plus DUCSA, ANCAP's distributor); the `emisor` actually stored is the station's own text as it came, so the report doesn't lose which station a fill-up happened at, and a mini-market line from that same station isn't forced into "Transporte" (the category is still an editable suggestion in review, same as vía 2). `contieneMarca` delimits the brand against letters, not `\b`, because "DISA" is short enough to match inside "PARADISA" with a word boundary, but must still match glued to a pump number ("ANCAP3140").
  - **A hand-mapped alias wins over both the direct-rubro name and the raw POS text**, for `emisorId` and for the displayed name (`emisorSugerido`) alike — previously the alias only resolved the id, and the name shown to the user stayed the raw POS text even when an alias existed. `LineaAnalizada.emisorDesdeTexto` (`estado-cuenta.ts`) flags whether the suggested emisor came from raw text (no alias yet) rather than a canonical name, and it's that flag — not `rubro === null` — that decides whether learning the alias on import is worth it: it now applies to fuel too (where the emisor is the station), but not to a fixed name like CVU/Apple, where the text carries a receipt number and every month would mint a different alias.
- **Chat assistant** (`/reportes/asistente`, `src/app/actions/chat-ia.ts`, `src/lib/chat-ia.ts`, `src/lib/ia-cliente.ts`, `src/components/chat-ia-view.tsx`): persistent conversations with the configured AI provider, about the user's own spending. LLM APIs have no memory between calls, so the history lives in `conversacionesIA`/`mensajesIA` and is re-sent on every message.
  - **The report is not injected automatically, and its JSON never passes through the browser.** It is generated server-side by `exportarReporteJSON`, stored in `reportesAdjuntos` and referenced by id: the chip above the textarea carries only a label and a token count, `enviarMensaje` takes an `adjuntoId` and concatenates the JSON server-side (report first, question after). Sending the JSON as a server-action argument — which is what this replaced — risks the 1 MB `serverActions.bodySizeLimit`: a multi-month report crosses it, and Next throws the 413 while deserializing, so no `try/catch` of ours ever sees it (see `lib/subidas.ts`).
    - **Two ways in, one mechanism.** `/reportes` has an "Analizar con IA" button (`dialogo-analizar-ia.tsx`) that exports *the filters currently applied* to a new conversation (picking provider and model) or to an existing one; the paperclip inside the chat exports the current month in one click and can re-attach a previous report of that thread. Both go through `prepararReporteParaChat`, so there is exactly one path and one size limit.
    - **The dialog warns when the report won't fit** in the chosen conversation's `limiteContexto`. That check belongs there because provider and model are already frozen in an existing conversation: the same report fits in one thread and not in another, and past the ceiling `podarHistorial` sends it truncated and the model reasons over mutilated data without saying so.
    - **An attachment only exists inside a conversation** (FK with cascade). At most one `pendiente` per conversation — the chip is one. Once sent, the JSON is *also* copied into the message's `contenido` (what was stored must be literally what was sent to the model: `tokensEstimados`, `podarHistorial` and `separarReporteAdjunto` all depend on it), so the table is a mailbox, not the archive — `usadoEn` marks the first send and only the last 5 used rows per conversation survive. Discarding a never-sent attachment deletes the row: it wasn't copied into any message.
  - **Provider and model are frozen per conversation, and are picked when creating it** (`crearConversacion({proveedor, modelo})`, `dialogo-nueva-conversacion.tsx`). Switching providers mid-thread would mix behaviours and (for Anthropic) throw away the cache, which is keyed by model — so changing provider means starting a new conversation. Choosing here does **not** move the app-wide default in `/ajustes`: it's a decision about this thread. The model field is free text with a `<datalist>` of `modelosSugeridos` (from `obtenerProveedoresDisponiblesIA`), never a closed `<select>` — same reason as in `/ajustes`, model ids rotate. `SelectorModeloIA` (`src/components/selector-modelo-ia.tsx`) is the one picker shared by both dialogs that can create a conversation (`dialogo-nueva-conversacion.tsx` and `dialogo-analizar-ia.tsx`) — an `idPrefijo` prop keeps the `<label htmlFor>`/`<datalist id>` pairs unique when both could theoretically mount at once.
  - **What actually blocks an oversized message is `estadoCuota`, not `presupuestoRespuesta`.** `podarHistorial` runs first and truncates the attached report down to `limiteContexto`, so by the time `presupuestoRespuesta` sees the input it already fits and returns a number — its `null` path is unreachable for an attached report. The rejection happens one step later, when `estadoCuota` compares requested tokens against the provider's TPM (verified with Groq: ~9,800 tokens vs. 8,000 TPM → refused with no fetch and no `usoIA` row, since both `registrarUso` and `llamar` come after that check). Know this before changing either function.
  - **History is pruned per request, never truncated in the DB** (`podarHistorial`). The newest messages that fit in `limiteContexto(proveedor)` are sent; the rest stay alive in the table and come back if the conversation shortens. A single message too big to fit alone is sent truncated with an explicit `[…contenido recortado…]` marker rather than dropped. This is what guarantees no message ever fails for size. `esResumen`/`archivadoEn` exist for a later manual-compaction delivery and are unused for now.
  - **On a failed provider call, the user's just-inserted message is deleted** (`enviarMensaje`, step 9) and its text returned so the UI can restore it. This is not optional: leaving it would end the thread on a `user` turn with no `assistant`, and the next request would send two consecutive `user` turns — a 400 from Anthropic (`roles must alternate`) and silent degradation elsewhere. Corollary the rest of the code may rely on: **`mensajesIA` never holds a `user` turn without its `assistant`**, except during the call itself.
  - **Always read history `ORDER BY id`, never by `creadoEn`.** Both messages of a turn are written within the same second, so a timestamp sort leaves their order undefined — and a history with the roles swapped is exactly what breaks a conversation.
  - **`PROMPT_SISTEMA_CHAT` is a frozen constant** — no interpolated date, provider name or anything dynamic. It sits at the front of Anthropic's cache prefix, and any byte that changes between requests invalidates the whole cached history behind it.
  - **Anthropic prompt caching** (`cachear`, dead code until an Anthropic key exists — see the providers note above): two breakpoints, one closing `system` and one on the **second-to-last** turn, so each request reuses the whole prior conversation as its prefix. Marking the *newest* turn instead is the classic mistake — it writes a fresh cache entry nobody ever reads. When caching, **every** message is emitted as a block array even without `cache_control`: the cache is a byte-level prefix match, `"r2"` and `[{type:"text",text:"r2"}]` are different bytes, and since the breakpoint advances each turn, a message changing shape as it loses its mark would silently invalidate the prefix every time.
  - **Model output is cleaned before storage** (`limpiarRespuestaChat`): `<think>`/`<thinking>` blocks stripped, and a code fence unwrapped *only* when it wraps the entire response — a fence in the middle is a legitimate code block. Same principle as `extraerJSON`, lighter because this is prose for a human.
- **Upload limits** (`src/lib/subidas.ts`): anything the browser sends the server travels as a server-action argument, and that payload is capped at **1 MB** (`serverActions.bodySizeLimit`, left at its default). Going over is not a catchable error — Next throws a 413 while *deserializing* the action, before a line of our code runs, so the component's `try/catch` never sees it and in production it reaches the browser as an opaque "Minified React error #441". That is exactly what a photo taken with a phone camera did. This module is the single place that knows about the limit: `prepararImagen`/`capturarVideo` rescale to 1600 px on the long side and re-encode as JPEG (dropping *quality* through 0.8/0.6/0.45, never resolution — resolution is what keeps prices legible for the model) and throw a readable error if it still doesn't fit, while `/estado-cuenta` calls `excedeLimite(file)` on the PDF before sending and shows `LIMITE_SUBIDA_BYTES` next to the upload button. The limit is stated as the same number that is checked. `createImageBitmap(..., { imageOrientation: "from-image" })` is not decoration: without it an EXIF-rotated portrait photo reaches the model sideways.
- **Every page that reads the DB must `export const dynamic = "force-dynamic"`.** Server actions reading SQLite don't mark a route as dynamic, so `next build` prerenders it and production serves data frozen at build time (invisible in `npm run dev`, which always re-renders). Add it to any new page that touches the DB.
- Dark, warm theme with a sage accent defined in `src/app/globals.css` — do not change the palette/typography when doing data-wiring work.
- **Deployment**: runs locally only — SQLite + `better-sqlite3` rule out Vercel/serverless (ephemeral FS, no shared state between invocations). Remote access is via Tailscale (`npm run serve` + `tailscale serve --bg 3000`), which is why there is no auth: the tailnet is the access boundary. See README.

### Data model (`src/db/schema/`)

Domain concept: Uruguay's mandatory e-invoicing (CFE) puts a QR code on receipts encoding `RUC_emisor,tipoCFE,serie,numero,monto,fecha,hash`. Each issuer (`emisor`, keyed by RUC) uses one of several third-party "proveedor de CFE" services (e.g. Scanntech) to look up receipt detail — there's no way to resolve this automatically, so it's a manually-maintained mapping. The QR payload format, why the DGI lookup URL resolves only validity (not merchant or processor), and the per-issuer processor POST behavior are all documented in `src/lib/cfe.ts`.

- `categorias` — id, `nombre` (unique), `color` (for charts), `descripcion` (free-text keywords used by `sugerirCategoriaPorTexto` in `actions/catalogos.ts` to suggest a category when a scanned item doesn't match the catalog), `esServicio` (default `false`, so no existing category changes behaviour — see the líneas de servicio notes above).
- `proveedoresCfe` — the e-invoicing providers themselves: `id`, `nombre` (unique), `urlConsulta` (required), `formato` (`text({enum})` from `FORMATOS_PROVEEDOR_CFE`, default `"otro"` — which request/parse implementation `consultarProcesador` uses; see the QR/CFE flow notes above). The consult URL belongs to the *provider*, not the merchant — every Scanntech merchant POSTs to the same endpoint — so it lives here once instead of being duplicated per issuer. Switching a merchant's provider is repointing one FK; past gastos are unaffected because the URL is only read live at scan time.
- `emisores` — unifies "merchant" and "CFE issuer": `id` (PK), `nombre` (required — the merchant name), `ruc` (nullable, unique — filled in once a receipt's RUC is mapped), `proveedorCfeId` (nullable FK → `proveedoresCfe`, `onDelete: restrict` so a provider still in use can't be deleted), `esGenerico` (flag for a generic catch-all merchant for one-off purchases not worth cataloging). A gasto with no receipt still points at an `emisores` row — just one with `ruc: null`.
- `itemsCatalogo` — reusable catalog of purchasable items (nombre, marca, tamano, `categoriaId` as a *suggested default*, not binding, `descripcion` for free-text search matching).
- `gastos` — one row per receipt/expense: fecha, `emisorId` (FK), and nullable CFE fields (`tipoCfe`, serie, numero) — null when logged without a receipt (cash, no invoice). A partial unique index on `(emisorId, serie, numero)` (WHERE `serie IS NOT NULL`) prevents loading the same receipt twice. `gastoFijoId` (nullable FK → `gastosFijos`, `onDelete: set null`) marks the gasto as the payment of a recurring template.
- `gastosFijos` — the recurring-expense templates behind `/gastos-fijos`: `nombre`, `categoriaId` (FK — doubles as the "tipo"), `emisorId` (nullable FK; without it the payment goes to the generic emisor), `importe` (the *expected* amount, nullable — `NULL` = not known yet; for UTE/Antel it varies and gets overwritten with each payment as next month's default) and `activo` (archived instead of deleted). No `UNIQUE` on `nombre`: it's a handful of rows the user sees all at once in one grid, so a constraint there is only error paths to write.
- `gastoItems` — line items of a gasto: `gastoId` (FK, cascade delete), `itemCatalogoId` (FK), `categoriaId` (FK — can override the item's default category per line), cantidad, `unidad`, precio, `esHormiga` (impulse vs. necessary spend flag), `esPesoDesconocido` (a kg/L line whose ticket didn't print the weight — see the Gasto form notes above; excluded from price-reference and sobreprecio math everywhere it's computed).
  - **`unidad` (`"un"` | `"kg"` | `"L"`) is what makes price comparison meaningful.** For variable-weight products (produce, cheese/deli, meat, bread by weight) the weight *cannot* live in `itemsCatalogo.tamano` — `0.150 kg` is what *that purchase* weighed, not a property of "Cebolla colorada"; storing it there forces a new catalog item per purchase. The catalog item stays generic and the weight goes on the line: with `unidad = "kg"`/`"L"`, `cantidad` is the weight and `precio` is the **price per kilo/litre**, so the total is still `cantidad × precio` and two purchases of different weights are directly comparable. Fixed-format packages (Leche 1L, Azúcar 1kg, Huevos x6) do keep `itemsCatalogo.tamano` and stay `unidad = "un"`.
  - Price references are keyed by **item + unidad** (`claveReferencia`, deliberately duplicated in `actions/gastos.ts` and `actions/reportes.ts` because a `"use server"` file can only export async functions) — a per-kilo price is never compared against a per-piece one. The by-weight margin (3% by default) applies only to kg/L, where POS rounding makes the per-kilo price inexact. See `src/lib/precios-referencia.ts` for the rationale.
- `configuracion` — key/value settings table (see AI providers above and `src/app/actions/configuracion.ts`): IA provider/model/API-key/rate-limiter state, plus advanced thresholds (`margenSobreprecioPeso`, `ventanaMesesReferencia`) and BCU/DGI/IA endpoint URLs and timeouts, all editable from `/ajustes`.
- `cotizaciones` — cache of BCU USD quotes keyed by requested date (`fecha`), storing the date actually quoted (`fechaCotizacion`, may be earlier — see `src/lib/bcu.ts`) so the same date isn't re-queried per statement line.
- `reportesAdjuntos` — a report exported from `/reportes` and waiting to be sent (or already sent) in a conversation: `conversacionId` (FK, cascade delete), the `json` itself, a human `etiqueta` describing the slice, the serialized `filtros` (to regenerate the same slice), `tokensEstimados` (computed with *that conversation's* provider), `pendiente` (the chip; at most one per conversation) and `usadoEn` (first send; `NULL` = never sent, so discarding it deletes the row). See the chat-assistant notes above for why the JSON lives here instead of travelling from the browser.
- `conversacionesIA` / `mensajesIA` — the chat assistant's persisted threads (see above). The conversation pins `proveedor`/`modelo`; each message carries its role (`user`/`assistant`, stored exactly as the providers expect — Gemini's `"model"` rename happens only when building the request), its estimated token cost, and the `esResumen`/`archivadoEn` columns reserved for future compaction. Timestamps are full ISO 8601 written from JS, not SQLite's `current_timestamp` (which emits UTC without subseconds and would clash with the rest of the app's local-time dates).
- `emisorAlias` — maps a POS statement name to an `emisores` row (FK, cascade delete) for statement-import matching; mapped by hand once, resolved automatically after.

When changing `src/db/schema/*`, run `npm run db:generate` to produce a new migration under `drizzle/`, then `npm run db:migrate` to apply it.
